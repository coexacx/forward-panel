# 连接回收与 EOF 修复

## 现象与原因

0.3.7 修复了 TCP 结束阶段的资源滞留。客户端可能已经完成握手，却在发送协议请求前收到 EOF 或连接重置；Agent 在线、端口监听正常，也没有进程重启。

旧逻辑在两个方向都读到 EOF 后，继续等待发送队列清零。连接随后被对端复位时，Linux 的 TCP 序号差值可能仍非零，但 socket 已进入 TCP_CLOSE，不再可能确认这些字节。旧逻辑会一直等待，同时保留两端 socket、连接计数、套餐连接额度及内存预算，最终拒绝新连接。

现场读取到 588 个已经关闭的 TCP socket，对应 294 条滞留连接；294 个 socket 的发送队列计数仍大于零。这不是进程 RSS 持续上涨，而是逻辑预留未释放。增加连接数或内存上限只能延迟再次出现，重启也只能暂时释放资源。

Linux 的 [SIOCOUTQ 实现](https://github.com/torvalds/linux/blob/master/net/ipv4/tcp.c)使用 TCP 序号计算结果；本修复结合 [TCP_INFO](https://man7.org/linux/man-pages/man7/tcp.7.html)检查实际连接状态。

补充检查还复现了单侧读到 EOF 后再收到复位的情况：该方向的读取已结束，而另一个方向仍等待数据，旧逻辑会等到对端关闭或读取超时才释放资源。此路径也纳入 0.3.7 修复。

## 修复行为

- 发送队列非空时同时检查 TCP 状态，已关闭连接立即结束等待并释放资源。
- 每次检查都覆盖连接两端，避免一端仍待确认时漏查另一端的关闭状态。
- 一端读到 EOF 后，每 250 ms 检查两端的终止状态；另一端即使继续保持连接，已复位的一端也会触发整条转发资源回收。正常双向传输不增加轮询。
- 仅在 TCP_CLOSE 时读取并处理 SO_ERROR，避免把 Linux 的临时软网络错误当作连接终止；描述符及检查任务受原连接生命周期约束，不产生脱离连接的后台任务。
- 保留正常慢速接收、TCP 半关闭与 ACK 等待，不使用额外固定的短超时切断健康传输。
- 转发中的读写、流量累计、套餐限额、达量暂停和多网卡监听保持原有规则。
- TCP_INFO 仅查询 Agent 自己持有的 socket，无需新增权限或修改系统网络参数。

## 验证

旧版在一次“半关闭后带未确认数据复位”的回归测试中就无法将连接计数归零。修复后分别模拟客户端复位与目标端复位，各连续 1,000 次；每次均验证连接计数和套餐额度回收，并在结束后完成正常数据传输。

另以 12 条规则、两份各含 6 个 TCP/UDP 额度的套餐验证并行回收：384 次正常关闭 / 复位混合循环、UDP 30 秒空闲回收、删除部分规则不影响其余连接、暂停后复用原端口和全部额度。额外覆盖客户端 / 目标端单侧 EOF 后复位，发送队列为空和非空的四种组合，另一端始终保持打开。

28 项实际执行的 Rust 测试通过，包含独立双网卡网络测试。编译后的静态二进制在 Debian 测试节点的隔离网络中完成 10 项真实网络测试。详细结果见 [验收记录](验收.md)。

## 更新

更新主控及 Agent 至 0.3.7 或更新版本。升级 Agent 会释放旧进程滞留状态，现有连接需要重连；规则、地址、端口、套餐和持久化流量不变。不要删除流量日志，也不要通过取消资源预算来处理这个问题。
